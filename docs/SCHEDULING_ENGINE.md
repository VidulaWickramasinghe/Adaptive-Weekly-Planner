# Weekly scheduling contract

A PlanningWeek is a Sunday local date and IANA zone. Convert that Sunday and the following local Sunday independently to instants. Every Interval is [start, end), with end strictly after start. Store elapsed minutes for task duration. Expand recurring wall-clock commitments in their own zone before clipping to the planning week. Include previous-day and previous-week intervals whose spans or buffers reach into the week.

The input snapshot contains the planning instant, input version, commitments and exceptions, protected rules, task instances, reserved routines, existing blocks, completions and preferences. Each task instance has a stable key, target minutes, minimum chunk, split flag, release, optional hard deadline, priority and preferences. The output contains preserved blocks, proposed changes, conflicts, unplaced instances with reason codes, and minute totals. Domain functions perform no writes.

1. Validate and expand only supported recurrence rules within the requested window, with a limit on occurrences and iterations. Apply exceptions by original occurrence identity. Report unsupported rules or exhausted limits before publishing availability. For nonexistent or ambiguous local times require resolution when entering an event, and flag future affected series occurrences for review. Changing the display zone preserves existing event instants and series zones.
2. Expand fixed intervals by preparation and travel. Union confirmed intervals, protected time and occupied locked or completed blocks. Cancelled events release their time. Proposed default for tentative events is a visible warning and preference to avoid them. Report conflicts between immutable commitments without moving either.
3. Materialise weekly demand by stable instance keys. Three sessions produce three instances. Carry overdue work forward by referencing its existing instance. Keep checklist-only routines outside capacity. Preserve accepted allocations if feasible, and keep completed minutes even when template targets change.
4. Find free intervals by subtraction. Apply release time, hard deadline, configured hard daily limits, rest, minimum chunk, split permission and week bounds before ranking. Count actual elapsed minutes. Prefer whole sessions. For a split, reserve all chunks together only if the whole target fits and each chunk meets its minimum.
5. Process eligible tasks by earliest hard deadline (undated last), then priority and stable ID. Compare feasible placements lexicographically by number of unaffected blocks moved, repeated sessions already on the same day, projected daily load relative to capacity, preferred day/window/energy mismatches, distance from previous placement, then start instant. Enumerate minute-aligned candidates with a stable ordering. Use the same inputs, clock and policy version for replay.
6. On a roster change first search using only displaced flexible blocks, freezing all others. If a higher-priority obligation still cannot fit, try a bounded second pass and identify every additional move for review. Never move completed, locked or confirmed items. Report a deadline, insufficient contiguous time, insufficient total capacity or search limit as appropriate. A bounded search failure is not proof of infeasibility.
7. Sum capacity from interval unions. Total elapsed week minus the union of fixed and protected time gives usable flexible time. Attribute overlaps once in the breakdown, fixed first. Deduct occupied flexible time within usable intervals to obtain remaining time. Show conflicts separately. Compare proposed and accepted totals explicitly.

**Roster example.** A Wednesday shift from 13:00 to 19:00 with 30 minutes of travel before it displaces a 13:00 study block. A 10:00–11:00 opening is eligible if it satisfies the task rules. The proposal shows both times and the reason. If the only opening is 40 minutes and the session needs an uninterrupted hour, show it as unscheduled. Rejecting the proposal keeps the original conflict visible. Accepting it updates the flexible schedule and records the revision.

## Current Phase 3 implementation

src/domain/schedule.ts implements the initial deterministic whole-session and splitting heuristic. The current UI exposes earliest release, hard deadlines, daily allowed hours, minimum chunk length and daily flexible capacity. It preserves existing allocations and reports existing conflicts. Tentative events are conservatively reserved.

The capacity display reports elapsed week minutes, proposed work minutes and remaining free minutes inside the selected daily window after reservations. It does not treat that free-time figure as a promise that further tasks satisfy workload or deadline restrictions. Advanced scoring dimensions remain later refinements. Phase 4 adds the focused relocation behavior below.

## Phase 4 domain implementation

[revisions.ts](../src/domain/revisions.ts) overlays accepted chunks on original occurrences, identifies directly conflicting eligible task sessions, freezes unaffected reservations and calls the placement heuristic with only displaced and unallocated demand. Results carry original occurrence identity and before spans. No extra task instances are created for splitting. If an affected session cannot fit, the proposal explicitly makes it unallocated. Sessions partly outside the selected week remain frozen to avoid replacing a partial group. Cross-week repair and a second pass that moves unaffected activities are not implemented.

[Revision unit tests](../tests/unit/revisions.test.ts) cover deterministic relocation, preservation of fixed/locked/completed/past and unaffected sessions, unallocated demand, recurring occurrence identity, split rendering, regeneration and cross-week preservation. Database acceptance and the complete browser workflow passed local verification on 23 November 2026; see the development plan.

## Progress semantics

The progress domain attributes scheduled minutes to each local day/week by interval intersection. A completed scheduled session contributes its planned duration, not a measured focus timer. A split session contributes all of its in-range chunks but counts once by task/occurrence identity. Completed scheduled history remains visible after archiving. Unscheduled tasks contribute their estimated duration to the week of their recorded completion timestamp; legacy undated completions are not assigned an invented date. Reopening removes the current completion from the review.

The Today selector uses the supplied planning instant and zone. Daily checklist routines use their separate occurrence records, excluding skipped dates. Productive and recreational screen time is stored separately and never added to these task totals. Portable calendar export receives an explicit timestamp, escapes text and folds UTF-8 lines without splitting characters.
